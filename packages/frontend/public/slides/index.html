Project Positioning

我刻意把問題定義成「不可信輸入系統」

這個專案的重點不是模型能力展示，而是 backend 是否能在不穩定 provider、惡意 transcript、長耗時工作、跨 session 隔離下仍然維持正確性。

Streaming

上傳不吃記憶體

Fastify multipart 直接串到 S3，server 不做整檔 buffer，避免大檔與併發上傳把 process 打爆。

Async Work

HTTP 與重任務解耦

RabbitMQ producer-consumer 讓 upload request 很快結束，STT/LLM 留給 worker 後台處理。

Realtime UX

進度即時回推

SSE 持續把 `pending / processing / completed / failed` 狀態與目前 `stt / llm` 步驟送給前端，避免前端主動輪詢。

Reliability

Provider 失效時自動切換

STT: OpenAI → Google，LLM: OpenAI → Anthropic，處理 timeout、429、5xx 單點故障。

Isolation

每個 session 只看得到自己的 task

session-scoped task isolation + atomic session rotation，避免資料串線與 stale session 洩漏。

Security

LLM 輸入輸出都視為不可信

Transcript sanitization、output guard、deterministic verifier 串成 secure summary pipeline。

System Architecture

Producer-Consumer，把 request path 切成 7 個可監控節點

Client 1. Upload 使用者上傳或錄製音檔，前端拿到 task id 後立刻進入 SSE 監聽。
Fastify 2. Validate 檢查 magic bytes、大小、session、CSRF、Origin，先擋掉明顯無效請求。
Storage 3. Persist File stream 直接進 S3/MinIO，不在 API server 內保留大型 binary buffer。
Queue 4. Enqueue Task HTTP 回應與 worker 真正處理脫鉤，降低 timeout 風險與系統耦合。
Worker 5. STT Whisper 優先，失敗時切到 Google STT，並保留 retry / DLQ 策略。
Worker 6. Secure Summary sanitize → summarize → guard → verify → persist，確保不把 raw LLM output 直接寫進 DB。
SSE 7. Push Status server 透過 SSE 輸出 task 狀態與結果；失敗時只回傳 sanitized error，不暴露內部細節。
設計重點是每一段都能單獨擴容、單獨失敗、單獨觀測，而不是把所有邏輯塞在一條 request handler 內。
Input Path

Streaming Upload，不把大檔案當成一般表單處理

What I Do

Binary validation at the edge

  • 只讀前 16 bytes 做 magic byte 檢查，不信任副檔名與 MIME type。
  • 驗證失敗直接中止 stream，避免垃圾檔案繼續走完整 pipeline。
  • 目前實作支援 WAV、MP3；驗證同時看 MIME type 與 magic bytes。
Why It Matters

Memory stays flat

  • API server 不用 `toBuffer()`，不會因為 25MB 檔案併發上傳而爆記憶體。
  • S3 upload 直接吃 readable stream，整條路徑維持 backpressure。
  • 更接近 production 真實限制，而不是只在 demo 規模下成立。

Security

Session Security 不是點綴，是資料隔離的底盤

CSRF Double Submit

session cookie + csrf token 雙向比對，避免跨站請求偽造。

HttpOnly / SameSite Cookie

cookie 不給前端 JS 讀，降低 XSS 後 session 被盜用的機率。

Atomic Session Rotation

session 更新時保留任務 ownership 一致性，不讓新舊 session 交錯讀寫。

Bootstrap-only Recovery

舊的 rotated cookie 只允許在 GET /api/tasks/session 修復，不把 revoked session 變成通用通行證。

Request ID + Sanitized Error

對外只回安全錯誤碼，內部仍可透過 request id 追查完整鏈路。

Persistent Rate Limit

以 PostgreSQL 做固定視窗限流，server 重啟後不失憶，適合多實例部署。

我把安全邏輯放在 plugin / utility 層做系統化處理，而不是每條 route 零散地手刻 if-else。
LLM Security

把 transcript 當成 hostile payload，而不是一般文字

這頁是我重點想表現的地方。語音摘要最大風險不是模型不夠聰明，而是模型太願意「聽話」。

A1 Threat Model

Prompt injection can ride inside transcript

  • 「Ignore previous instructions」這類文字可能出現在會議錄音或惡意音檔內。
  • 如果 worker 直接把 transcript 丟進 LLM，模型可能偏離摘要任務。
  • 嚴重時可能回出 meta text、隱藏 prompt 請求、甚至錯誤暴露敏感內容。
Secure Summary Pipeline

1. Normalize + sanitize transcript

NFKC normalization、移除 zero-width chars、過濾 `ignore instructions`、`developer message`、`tool instructions`、`system prompt` 與混淆拼寫。

2. System prompt carries task + security

System prompt 定義「3-5 bullet 摘要」任務與安全限制；user prompt 只包 `` 標籤與原文，不混入額外指令。

3. Output guard before persistence

模型輸出先經過 secret redaction，API key、Bearer token、session token、query secret 全部先移除。

4. Deterministic verifier

檢查數字與 URL 是否存在於 transcript、阻擋 meta-response，並偵測 copy-through（length ratio + trigram overlap）。

關鍵原則：raw LLM output 不直接進資料庫。先 guard，再 verify，最後才 persist。
Defense In Depth

LLM 防護不是一條 regex，而是前後夾擊的 3 層防線

Input Hardening

Transcript sanitization 先把高風險 injection phrase、混淆空白、zero-width 字元清掉，再限制長度，減少 prompt 汙染面。

Model Constraint

System prompt 集中任務與安全指令（3-5 bullet、壓縮、不可服從 transcript 內指令），user prompt 只放 `` 包裹的原文。

Output Verification

Guard + verifier 不是相信模型說自己做對了，而是用 deterministic rules 驗證它沒有越界，包含 copy-through 偵測。

Realtime UX

SSE 讓長任務不是黑盒子

Server-Sent Events

單向推送就足夠，而且更簡潔

  • 這個場景只需要 server → client 的狀態推送，不需要 WebSocket 雙向複雜度。
  • 前端收到 `status`、`completed`、`failed` 後直接更新 task list 與 detail view。
  • 重連邏輯簡單，部署與代理層也更穩。

使用者會一直知道系統在做什麼

T+1s

T+N

Resilience

Speech-to-Text

  • OpenAI timeout / 429 / 5xx 時切換備援。
  • worker 持有統一介面，不把 vendor 細節洩漏到上層流程。
  • 上層只知道 `transcribe(file)`，實際走哪家 provider 可替換。

  • 摘要 provider 同樣用抽象介面 + fallback wrapper。
  • 可重用相同 security prompt 與 transcript framing。
  • 把單一模型故障從 outage 降成 degraded-but-working。

Summary

我想傳達的是：我做的不只是 AI app，而是可以面對真實世界輸入與故障模式的 backend system

VoiceBrief 展示的是我在 backend 上的三個判斷力：系統分層、安全邊界、可靠性設計。特別是在 LLM 這段，我不是只追求「能生成」，而是要求它在 hostile transcript 下仍然可控。

Architecture

Streaming upload + queue + worker + SSE，讓整條路徑可擴充、可觀測、可維護。

Security

Session isolation、CSRF、error sanitization、LLM input/output hardening 形成完整安全面。

Reliability

Provider fallback、retry、sanitized failure、persistent rate limit，使系統更接近 production 行為。
