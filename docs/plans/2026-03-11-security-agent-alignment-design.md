# internal Security And Agent Alignment - Implementation Design

## Goal

Bring `stt-summary-server` into alignment with the security and agent-control standards used in the internal security reference project, with implementation guidance detailed enough for Claude Code CLI to execute without making architectural assumptions.

This is a major change. The work must be implemented as a coordinated security refactor, not as isolated patches.

## Primary Outcomes

After this work is complete, the project must satisfy all of the following:

1. Session management supports rotation and ownership migration, rather than long-lived fixed session IDs.
2. Rate limiting is durable across process restarts and horizontally scaled server instances.
3. Worker output is treated as untrusted and passes through a shared output-guard pipeline before being persisted or returned.
4. Summary generation has a deterministic verification step that checks summary fidelity against the transcript.
5. Server and worker logging both apply deep secret redaction, including nested error objects.
6. Server and worker IAM/runtime permissions are reduced to least privilege.
7. All changes are covered by automated tests at unit, integration, and regression level.

## Non-Goals

The following are explicitly out of scope for this change and must not be introduced incidentally:

1. No user account system.
2. No JWT or OAuth redesign.
3. No change from SSE to WebSocket.
4. No replacement of Fastify, Prisma, RabbitMQ, or PostgreSQL.
5. No speculative UI redesign in frontend.
6. No best-effort partial implementation of the verification flow. Either the full specified path is implemented, or the task is incomplete.

## Problem Statement

The current project has reasonable HTTP-boundary protections, but it does not yet match internal in the following critical areas:

1. The model output path is not guarded. The summary is generated by an LLM and stored/returned directly.
2. There is no verifier step to detect summary hallucination or transcript drift.
3. Sessions have TTL but no rotation despite the schema already containing `rotated_to`.
4. Rate limiting is process-local and does not remain effective across multiple ECS tasks or restarts.
5. Worker redaction only handles shallow string fields and can leak nested secrets from SDK errors.
6. Server and worker share the same broad runtime IAM role.

## Reference Standard From internal

Claude Code CLI must treat the following patterns from internal as the intended standard to adapt:

1. Shared secure pipeline for model output control.
2. Output guard before emission to clients.
3. Verification stage after generation.
4. Session rotation with ownership migration.
5. Durable rate limiting using persistent storage.
6. Deep secret redaction across logs.

This implementation is not required to copy internal file-for-file, but it must preserve the same control points and security properties.

## Required Change Set

The implementation must include all sections below.

## 1. Shared Summary Security Pipeline

### Objective

Create a single shared pipeline for summary generation that performs:

1. transcript sanitization before LLM invocation,
2. guarded summary generation,
3. output redaction on every generated chunk or final string,
4. transcript-summary verification,
5. safe persistence of only guarded output.

### Required behavior

The worker must no longer write raw LLM output directly into `tasks.summary`.

The required flow is:

1. Download transcript source.
2. Sanitize transcript text.
3. Generate summary with primary/fallback LLM.
4. Pass generated summary through output guard.
5. Verify the guarded summary against the sanitized transcript.
6. If verification passes, persist guarded summary and completion metadata.
7. If verification fails, mark task failed with an internal machine-readable failure reason and a sanitized external error.

### Required implementation shape

Create a new shared worker-level module, recommended path:

- `packages/worker/src/pipelines/secure-summary.ts`

This module must own the full orchestration of:

1. `sanitizeTranscript()`
2. LLM call
3. `guardModelOutput()`
4. `verifySummaryAgainstTranscript()`

Do not leave any of these steps split across unrelated files once the refactor is complete.

### Output guard requirements

Create a worker utility, recommended path:

- `packages/worker/src/utils/output-guard.ts`

It must redact at least these patterns:

1. OpenAI-style keys: `sk-[A-Za-z0-9_-]{20,}`
2. Session tokens: `sess-[A-Za-z0-9_-]{16,}`
3. Bearer tokens: `authorization\\s*:\\s*bearer\\s+\\S+`
4. API key assignments: `api[_ -]?key\\s*[:=]\\s*\\S+`
5. Base64-like blobs of length 32 or more: `(?<![A-Za-z0-9])[A-Za-z0-9+/]{32,}={0,2}(?![A-Za-z0-9])`
6. Query-string secrets: `token=`, `secret=`, `access_token=`, `api_key=`, `session_id=`

Replacement string must be:

```text
[REDACTED: sensitive content removed]
```

Do not use `[REDACTED]` in this module; use the exact notice above so tests can assert the stronger contract.

### Verification requirements

Create a worker verifier module, recommended path:

- `packages/worker/src/verification/summary-verifier.ts`

This verifier must be deterministic and must not call an LLM.

The verifier must check all of the following:

1. Every number in the summary must appear verbatim in the sanitized transcript, unless the number is part of a static bullet/index label introduced by formatting logic.
2. The summary must not contain URLs that are absent from the transcript.
3. The summary must not contain secret-like patterns after output guard; if it does, verification fails.
4. The summary must not exceed a configurable maximum length.
5. The summary must not be empty or whitespace-only.

### Verification result contract

Define a typed result:

```ts
interface SummaryVerificationResult {
  isConsistent: boolean;
  issues: string[];
}
```

If `isConsistent` is `false`, the worker must:

1. not store the summary,
2. mark the task as `failed`,
3. store an internal error that indicates verification failure,
4. expose only sanitized task error data through the API.

### Failure classification

Add machine-readable internal error categories:

1. `stt_failed`
2. `llm_failed`
3. `summary_verification_failed`
4. `processing_timeout`
5. `processing_internal_error`

Internal DB `error` text may contain the category prefix for debugging, but API responses must still go through existing sanitization logic.

## 2. Session Rotation And Ownership Migration

### Objective

Replace fixed 30-day session behavior with rotation-based session lifecycle aligned to internal's model.

### Required behavior

Keep the current cookie/session architecture:

1. HttpOnly `stt_session`
2. JS-readable `csrf_token`
3. UA hash binding
4. IP prefix binding
5. unsafe methods require valid session + CSRF + `Origin`

Add the following:

1. Session TTL remains 30 days.
2. Session rotation threshold becomes 24 hours.
3. On a valid request with a session older than 24 hours:
   1. create a new session row,
   2. copy binding data and generate a new CSRF token,
   3. set old session `rotated_to`,
   4. mark old session revoked,
   5. atomically migrate owned tasks to the new session ID,
   6. send updated cookies,
   7. continue request processing under the new session.

### Atomicity requirement

Rotation plus task ownership migration must happen in a single database transaction.

This is mandatory. Do not implement rotation and task migration as separate best-effort writes.

### Required schema behavior

Use existing `rotated_to` column in `sessions`.

Do not add a second rotation-tracking column unless absolutely necessary for referential integrity and documented in the migration notes.

### Server plugin requirements

Refactor `packages/server/src/plugins/session.ts` so that:

1. session validation,
2. session creation,
3. session rotation,
4. last-seen touch,
5. cookie issuance,
6. CSRF validation

are explicitly separated into small functions with unit-testable boundaries.

### Cookie requirements

Preserve current cookie names:

1. `stt_session`
2. `csrf_token`

Do not rename cookies in this change.

## 3. Durable Rate Limiting

### Objective

Replace process-local in-memory rate limiting with persistent rate limiting that remains effective across:

1. server restarts,
2. multiple ECS server tasks,
3. rolling deployments.

### Storage choice

Use PostgreSQL, not in-memory maps and not filesystem storage.

Reason:

1. PostgreSQL already exists in this project.
2. This avoids adding Redis as a new infrastructure dependency during this refactor.

### Required schema

Add a new table via Prisma migration, recommended model name:

- `RateLimitEntry`

Recommended fields:

1. `bucket` string
2. `key` string
3. `windowStart` timestamp
4. `count` integer
5. `updatedAt` timestamp

Add a composite uniqueness constraint on:

1. `bucket`
2. `key`
3. `windowStart`

### Required behavior

Implement a reusable rate limit service, recommended path:

- `packages/server/src/services/rate-limit.ts`

It must support:

1. fixed bucket name,
2. key,
3. current time,
4. window duration,
5. max allowed count,
6. atomic increment/check.

### Scope of limits

The following limits are mandatory:

1. `GET /api/tasks/session`: 5 per minute per IP
2. `POST /api/tasks`: 10 per minute per IP
3. `GET /api/tasks`: 30 per minute per IP
4. `GET /api/tasks/:id`: 30 per minute per IP
5. `GET /api/tasks/:id/events`: 5 per minute per IP

### IP source rule

Use the direct connection IP only, matching internal's security standard.

Do not trust `X-Forwarded-For` as a rate limit key source in application logic.

If Fastify proxy settings already normalize `request.ip`, document and preserve that mechanism; do not parse raw forwarded headers manually.

### Cleanup requirement

Add a cleanup path for stale rows older than a retention threshold.

Allowed approaches:

1. best-effort periodic cleanup during writes, or
2. a documented SQL cleanup task.

If periodic cleanup is chosen, it must be low-frequency and bounded.

## 4. Deep Worker And Server Log Redaction

### Objective

Align worker logging with the server's deeper redaction guarantees.

### Required behavior

After this change:

1. both server and worker must use recursive redaction,
2. nested objects and arrays must be traversed,
3. circular references must not crash logging,
4. error objects must be redacted after serialization,
5. string fields in nested request/response/error objects must be redacted.

### Server requirement

Server currently has deeper redaction already. Preserve behavior and expand tests where needed.

### Worker requirement

Refactor worker logger to match server capabilities.

Preferred implementation:

1. either extract a shared package-level redaction utility used by both server and worker,
2. or duplicate the same logic intentionally with identical tests.

Preferred option is shared utility to prevent drift.

### Logging prohibition

Do not add any `console.log`, `console.error`, or ad-hoc debug prints.

All new logging must go through the structured logger.

## 5. Worker Storage And Memory Safety

### Objective

Remove the current full-buffer S3 download behavior from the worker.

### Required behavior

`packages/worker/src/services/storage.ts` must no longer use `transformToByteArray()` for the main processing path.

Allowed designs:

1. stream S3 object to a temporary file and hand that file to providers, or
2. stream directly into provider SDK if the SDK accepts streams.

### Decision requirement

Claude Code CLI must inspect both STT provider clients and choose the simpler correct implementation.

Selection rule:

1. if OpenAI and fallback STT providers both accept file streams or file paths, use a temp-file approach;
2. if both accept streams safely, direct streaming is acceptable;
3. do not keep the current whole-object buffering path as the default implementation.

### Temp-file safety requirements

If temp files are used:

1. use OS temp directory,
2. generate random filenames,
3. remove temp files in `finally`,
4. ensure cleanup happens on both success and failure.

## 6. IAM Least Privilege Split

### Objective

Separate server and worker runtime IAM privileges.

### Required behavior

Do not keep a single shared ECS task role for both services.

Create distinct task roles:

1. server runtime role
2. worker runtime role

### Required permissions

Server role must have only:

1. `s3:PutObject` on uploads bucket objects

Worker role must have only:

1. `s3:GetObject` on uploads bucket objects

Do not grant wildcard S3 permissions broader than object scope.

### Execution role

Keep ECS execution role separate for:

1. pulling images,
2. reading Secrets Manager values,
3. CloudWatch log driver needs.

Do not move runtime S3 permissions into the execution role.

## 7. API And SSE Contract Changes

### Objective

Preserve current API shape where possible, but add structured handling for verification-related failure paths.

### Mandatory response behavior

The following API shapes must remain stable:

1. `GET /api/tasks`
2. `GET /api/tasks/:id`
3. `GET /api/tasks/:id/events`

Task success responses may keep existing fields.

Task failure responses must continue exposing only sanitized error payloads via `sanitizeTaskError()`.

### SSE requirement

Do not add new SSE event types unless required to expose verification failure distinctly.

If a new event type is added, it must be documented and tested. Preferred approach is to continue using the existing `failed` event with a new sanitized failure code.

### Error sanitizer changes

Extend `packages/server/src/utils/error-sanitizer.ts` to recognize:

1. verification failure
2. timeout failure
3. generic guarded-output failure

Suggested external codes:

1. `transcription_failed`
2. `summarization_failed`
3. `summary_verification_failed`
4. `processing_timeout`
5. `processing_failed`

Do not leak raw provider error strings to clients.

## 8. Frontend Requirements

### Objective

Ensure frontend behavior remains compatible with session rotation and sanitized failure semantics.

### Required behavior

1. `initSession()` must continue to bootstrap the session before upload.
2. Frontend must tolerate a rotated session and continue using the new CSRF token returned by `/api/tasks/session`.
3. Frontend must correctly surface new sanitized failure codes/messages without assuming only the previous two categories exist.
4. No frontend secret handling must be introduced.

### Explicit prohibition

Do not add localStorage/sessionStorage ownership tokens or task-access tokens as part of this refactor.

## Database Migration Requirements

### Migration ordering

Migrations must be safe for rolling deployment.

Required order:

1. add new tables/columns/indexes first,
2. deploy application code that can read/write both old and new state if needed,
3. only then remove obsolete code paths.

### Mandatory migrations

At minimum:

1. add `rate_limit_entries` table,
2. add indexes required for efficient rate-limit lookups,
3. ensure session rotation fields/indexes are sufficient,
4. add any needed task/session foreign key or index improvements for rotation transaction performance.

### Data migration rule

Do not rewrite all existing tasks eagerly unless strictly necessary.

Task ownership migration should occur on rotation transaction for the affected session only.

## Testing Requirements

Testing is mandatory. Claude Code CLI must write or update tests for every section above.

A change is incomplete if tests are missing, even if runtime behavior appears correct.

## Acceptance Criteria

The work is complete only if all conditions below are true:

1. No raw summary text from the LLM is stored before output guard runs.
2. Verification failure causes task failure and does not store a summary.
3. Sessions rotate after 24 hours and task ownership migrates automatically.
4. Rate limiting remains effective across multiple server instances using the same database.
5. Worker nested error logs are redacted.
6. Terraform defines separate server and worker task roles with least privilege S3 access.
7. Existing security tests continue to pass.
8. New tests covering all required behaviors are added and passing.

## Required Verification Commands

Claude Code CLI must run the relevant test suites and report results.

At minimum, run:

```bash
uv run pytest
```

If this repository does not use `uv` for JavaScript/TypeScript tests, then run the equivalent project test commands for this monorepo and include them in the implementation notes. The implementation is not done if the agent edits code but does not run the relevant test suites.

## Implementation Notes For Claude Code CLI

The following rules are mandatory during implementation:

1. Do not silently weaken a requirement because the current codebase is simpler.
2. Do not skip the verifier because "the transcript is already trusted enough".
3. Do not keep in-memory rate limiting as the main path.
4. Do not preserve direct raw-summary persistence for backward compatibility.
5. Do not split session rotation and task migration into separate writes.
6. Do not broaden IAM permissions beyond the scope defined above.
7. Do not omit tests for any new behavior.

If any requirement appears infeasible, stop and document the blocker explicitly rather than improvising a smaller solution.
